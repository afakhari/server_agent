# 24 · ممیزی انطباق با شرح رسمی چالش و اصلاحات اساسی

**منابع اصلی:** فایل کاربر «شرح-چالش.txt» و «متن-ترجمه-ویدیو.txt»؛ مستندات رسمی Liara OpenAPI و کد موجود شاخه feature/conversational-agent-langgraph. این سند صرفاً وضعیت کد را می‌گوید، نه مدرک اجرای واقعی.

## ۱. مقایسه معیارهای رسمی (جمع ۳۰۰ امتیاز)
| معیار داوری | امتیاز | امکانات فعلی | کمبود باقیمانده / مدرک ضروری |
|---|---:|---|---|
| اتصال و عملیات واقعی Liara | ۱۰۰ | LiaraClient: projects/logs/events/releases/metrics/domains؛ source upload/release و restart با one-use approval؛ CLI جایگزین | انجام کنترل‌شده Live Read و Live Write روی برنامه disposable، تأیید schema و هزینه؛ هنوز اثبات نشده |
| حل مسئله هوشمند | ۱۰۰ | evidence-driven diagnosis با فرضیه‌های چندگانه؛ advisory LLM اختیاری؛ brief کدنویسی قابل کپی | جمع‌آوری شواهد زنده و اثبات علّت/اصلاح واقعی کد و بررسی HTTP بعد از آن؛ Coding Agent فعلاً دستی |

## ۲. مهم‌ترین نکات از متن ویدیو
- کاربر برنامه‌نویسی است که ممکن است هیچ دانش دیپلوی نداشته باشد؛ بنابراین wizard نباید بدون توضیح، شناسه پلن یا پورت را فرض کند.
- شارژ حساب لیارا، انتخاب پلن با اطلاع کاربر، تنظیم دامنه و کارهای خارج از API بر عهده صاحب حساب است؛ agent باید مسئولیت‌ها را روشن کند.
- انتظار SRE موردی وجود دارد، نه الزام پایش خودکار شبانه‌روزی؛ شواهد، علت‌های احتمالی و پیشنهاد رفع مشکل مهم‌اند.
- هماهنگی با Coding Agent مطلوب است؛ در MVP فعلی تنها handoff ساختاریافته برای بازبینی انسان اضافه شده است؛ patch/PR خودکار **پیاده‌سازی نشده**.
- UI پرزرق‌وبرق ملاک نیست؛ کاهش اصطکاک، دقت معنی پیام و نشان‌دادن وضعیت کار معیار است.
- ویدئوی نمایشی حدود پنج دقیقه **اجباری** است. بدون ویدیو اثر از داوری حذف می‌شود.

## ۳. اصلاحات انجام‌شده در این دور
- `sentinel/onboarding.py`: نیازسنجی با الگوی ترافیک/سورس/پورت/دیتابیس/دامنه، راهنمای ظرفیت بدون ساختن price/planID و فهرست کارهای دستی اپراتور.
- `app.py`: endpoint خواندنی POST /api/onboarding/assess؛ در حالت private-server از صدور proposal اجرایی در /api/inspect جلوگیری شد.
- `sentinel/intent.py` و `sentinel/conversation.py`: پرسش انتخاب منابع/پلن وارد مسیر نیازسنجی می‌شود، نه پاسخ قیمت یا اجرای deploy.
- `frontend/src/App.tsx`: فرم قدم اول، بررسی آماده‌بودن، نمایش مراحل و موانع، هشدار اختلاف پلتفرم/پورت و invalidation پیش‌نمایش تغییرکرده.
- `sentinel/handoff.py` و رابط گزارش: بسته وظایف code review/تست رگرسیون با Evidence ID و کپی اختیاری برای Coding Agent بدون ارسال خودکار فایل یا secret.
- `sentinel/engine.py`, `sentinel/liara.py`: نمایش کران‌دار متریک خام CPU/RAM و تصریح نامعلوم بودن واحد و درصد.
- `tests/test_brief_acceptance.py`: آزمون‌های جدید مسیر onboarding، پیشنهاد غیرساختگی، محدودیت Live/Demo، handoff، تشخیص نیاز منابع و متریک خام.
- `SUBMISSION.md`: سند واحد معماری، اتصال، تعامل، محدودیت‌ها، ماتریس امتیاز و سناریوی دمو.

## ۴. شکاف‌های واقعاً باز (به‌ترتیب اهمیت)
1. **P0 · اثبات Live:** بدون توکن و حساب آزمایشی، رفتار واقعی API و استقرار/ری‌استارت آزموده نشده؛ نمی‌توان کامل‌بودن ۱۰۰ امتیاز Integration را ادعا کرد.
2. **P0 · ویدیوی مسابقه:** هنوز ویدیوی حدود پنج دقیقه ضبط نشده. این شرط داوری حذف‌کننده است.
3. **P0 · QA:** آخرین نسخه React پس از اصلاحات جدید build نشده؛ pytest و CI شواهد موفق ندارند. فایل frontend/package-lock.json تولیدشده روی دستگاه مالک هنوز در GitHub ثبت نشده است.
4. **P1 · انتخاب پلن واقعی:** توصیه منابع فقط preliminary و براساس نیازهای کاربر است، چون قیمت و catalog واقعی account-sensitive هنوز قرارداد live تأییدشده ندارد.
5. **P1 · Coding Agent واقعی:** مسیر فعلی صرفاً handoff دستی است. برای PR خودکار باید repo-scoped GitHub Auth و policy مستقل + بازبینی انسان طراحی شود.
6. **P1 · عملیات مدیریتی بیشتر:** plan resize, env.update, DNS mutation, rollback خودکار عمداً پشتیبانی نمی‌شوند و نباید بدون API validation و dry-run/approval معرفی شوند.
7. **P1 · ارزیابی UX واقعی:** تست RTL، contrast، keyboard، load state و همه خطاهای شبکه در مرورگر لازم است.
8. **P2 · پایش دوره‌ای:** بریف صریحاً ۲۴ساعته را اجباری نمی‌داند؛ قبل از تکمیل سناریوی end-to-end اولویت پایین‌تری دارد.

## ۵. معیار پذیرش حرفه‌ای
- خطای ۵۰۰ روی سرویس disposable، snapshot زنده و evidence با منابع واقعی، نتیجه اقدام/اصلاح و سلامت مستقل بعد از آن.
- انتشار اولین نسخه در محیط مجاز فقط پس از کنترل plan/cost، پروژه و محدوده اجازه، و بدون اعطای خودکار اختیار به LLM.
- اولین کاربر بدون پیش‌زمینه فنی بتواند بفهمد کدام مرحله انجام شده و قدم بعدی بر عهده چه کسی است.
- هیچ خطای شبکه یا پاسخ timeout، به کاربر به‌صورت موفقیت قطعی نمایش داده نشود.
- تست‌ها و بیلد آخرین SHA سبز و lockfile ثبت شده؛ استقرار آزمایشی HTTPS/backup/rollback آزموده شده.
- سناریوی ویدیوی پنج‌دقیقه‌ای با نتیجه واقعی، بدون داده ساختگی با برچسب Live، آماده و ضبط شده.

**نتیجه:** اصلاحات ساختاری حاضر کیفیت نام‌گذاری، نیازسنجی و گزارش SRE را ارتقا می‌دهند، اما دامنه عمل واقعی، ضبط ویدیو و تست زنده همچنان شرایط تکمیل مسابقه‌اند. اعلام DONE قبل از آن خلاف شرح چالش است.
