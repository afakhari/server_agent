# 23 · پوشش نیازهای کاربر، Intent Classification و Clustering

تاریخ بررسی: ۲۳ اکتبر ۲۰۲۶ · شاخه `feature/conversational-agent-langgraph`  
**وضعیت:** پیاده‌سازی سناریوهای زیر و تست‌های Golden افزوده شده‌اند؛ نتیجه اجرای تمام تست‌های جدید، بیلد React و تست واقعی مرورگر **هنوز ثبت نشده**. ادعای پوشش «تمام جملات ممکن» علمی یا عملی نیست؛ fallback امن برای ناشناخته‌ها بخش اصلی کیفیت تجربه است.

## ۱. اصل طراحی

**کاربر باید همیشه بداند:** Sentinel از پیامش چه برداشتی کرده، به کدام پروژه و حالت Demo/Live نگاه می‌کند، آیا اطلاعات واقعاً از Liara آمده یا نمونه است، آیا اقدام انجام شده یا فقط پیشنهاد شده، آیا نتیجه تأیید مستقل شده و قدم بعدی چیست.

- تک‌ورودی **conversation-first**، با کارت‌های گزینش‌پذیر و داده ساختاری.
- پیام روشن → مسیر متناظر، بدون پرسش اضافه.
- پیام چندهدفه مستقل → گزینه‌های مشخص، **بدون انتخاب خودسرانه**.
- پیام مبهم → راهنمای محدود و گزینه‌های منتخب، نه پاسخ ساختگی.
- پیام خارج از توان → محدودیت روشن و بدون وعده انجام کار.
- پیام حاوی token شناخته‌شده → redaction، جلوگیری از ارسال آن به مدل و پیشنهاد تعویض کلید.
- «بله»، «لغو»، «restart» به‌تنهایی **مجوز اجرای عملیات نیستند**. تأیید فقط از کارت معتبرِ actor/project/state-bound و one-time انجام می‌شود.
- بعد از خروج از کارت تأیید، مجوز قدیمی از مسیر چت قابل استفاده نیست؛ انقضای مجوز هم در کارت نمایش داده می‌شود.
- در `private-server` یا حالت Live بدون اجازه write، کارت اجرا برای restart اصلاً صادر نمی‌شود.
- وضعیت `SUBMITTED`، `HEALTHY_NOW` و `VERIFIED` مترادف نیستند.

## ۲. دسته‌بندی دامنه نیازها

| دسته هدف | مثال کاربر | پاسخ واقعی |
|---|---|---|
| شروع و راهنمایی | «سلام»، «از کجا شروع کنم؟» | معرفی کوتاه + پیشنهادهای اقدام |
| عیب‌یابی | «خطای ۵۰۰ می‌دهد»، «بعد دیپلوی خراب شد» | جمع‌آوری شواهد و فرضیه‌ها؛ restart فقط با مجوز |
| سلامت و منابع | «مصرف رم»، «CPU»، «سلامت سرویس» | بررسی read-only؛ محدودیت متریک‌ها آشکار |
| انتشار | «سایتم را منتشر کن»، «deploy my app» | Project Scout، preview و فرایند تأیید، نه نوشتن خودکار |
| فهرست پروژه‌ها | «برنامه‌های حساب» | Demo مصنوعی یا فهرست Live معتبر |
| انتشارهای گذشته | «آخرین نسخه»، «releases» | خواندن release metadata؛ عدم ادعای سلامت |
| دامنه / SSL | «SSL»، «CNAME»، «DNS» | مشاهده داده‌های ثبت‌شده؛ عدم تغییر خودکار DNS |
| لاگ | «لاگ‌های خطا» | تشخیص با evidence، نه نمایش ساختگی |
| قیمت و پلن | «هزینه چقدر است؟» | ارجاع به قیمت معتبر پنل؛ بدون ساخت رقم |
| محیط و امنیت | «ENV»، «توکن»، «دسترسی» | راهنمای امن و هشدار عدم ارسال secret |
| دیتابیس | «اتصال Postgres» | راهنمای محدود؛ بدون دسترسی مستقیم یا خواندن داده‌ها |
| بکاپ و بازیابی | «از دیتابیس بکاپ بگیر» | بیان نبود قابلیت خودکار + مسیر امن دستی |
| حساب تیمی | «پروژه‌های تیم» | نیاز به team ID سمت سرور؛ بدون دریافت آن از مدل |
| پشتیبانی | «با کارشناس حرف بزنم» | معرفی مسیر پشتیبانی، بدون ادعای ارسال تیکت |
| هشدارها | «وقتی خراب شد خبرم کن» | بیان نبود مانیتورینگ خودکار ۲۴/۷ |
| حذف / عملیات مخرب | «همه چیز را پاک کن» | مسدودسازی واضح و بدون write |
| تأیید متنی | «بله»، «اوکی» | راهنمای استفاده از کارت تأیید، بدون اجرای عملیات |
| رد / لغو متنی | «نه»، «لغو» | عدم اقدام؛ لغو واقعی مجوز روی کارت |
| چند درخواست | «هزینه و SSL را بررسی کن» | انتخاب یکی از اقدامات مشخص |
| درخواست ناشناخته | «چیزم کار نمی‌کنه» | عدم حدس و پرسش هدایت‌شده با گزینه‌های قابل انجام |

**محدودیت مهم:** این جدول contract واقعی ابزارها را تغییر نمی‌دهد؛ Chat به ابزارهای مجاز فعلی محدود می‌ماند. هیچ کارت یا classification نباید اجرای shell، حذف منابع، پرداخت یا تغییردادن قیمت را راه بیندازد.

## ۳. Classification: طراحی انتخابی

فایل `sentinel/intent.py` دارای classifier قابل‌توضیح است:

1. Unicode normalize برای حروف عربی/فارسی، اعداد فارسی/عربی، نیم‌فاصله و case انگلیسی.
2. شناسایی درخواست مخرب، عملیات خارج از توان، تأیید/لغو تک‌کلمه‌ای **پیش از** routing.
3. استخراج چند label هم‌زمان از vocabulary تخصصی DevOps و محیط Liara.
4. اولویت «خرابی واقعی» بر «انتشار» برای جملاتی مثل «بعد از دیپلوی خطای ۵۰۰ دارم».
5. تشخیص modifierها: «بکاپ دیتابیس» یک نیاز backup است؛ «فهرست پروژه تیمی» یک نیاز projects.
6. انتخاب یک route فقط زمانی که تفسیری نسبتاً روشن وجود دارد.
7. اگر اهداف مستقل متعدد باشند: کارت گزینه‌ها، نه اجرای تصادفی یک مسیر.
8. برای unknown: پیشنهادهای محدود و بدون عملیات. LangChain اختیاری می‌تواند **فقط یک گزینه پیشنهادی** تولید کند؛ تصمیم model ابزار اجرایی را تغییر نمی‌دهد.
9. خروجی شامل `intent`، `route`، `certainty` و `labels` است. در UI با برچسب «برداشت اولیه» نشان داده می‌شود؛ confidence ساختگی درصدی ارائه نمی‌شود.

قصد کاربر فقط شاخص هدایت است؛ مالکیت پروژه، اجازه restart، قابلیت ایجاد برنامه و وضعیت سلامت فقط توسط adapter / policy / evidence اثبات می‌شوند.

## ۴. Clustering: کجا مفید است و کجا نه

Clustering هدفش **کشف موضوعات پرتکرار ناشناخته برای بهبود محصول** است، نه تصمیم آنلاین برای endpoint عملیاتی. روی جمله‌های کوتاه فارسی embedding-clustering در داده کم می‌تواند عبارت‌های نامرتبط را ادغام کند و توضیح‌پذیری کمتری نسبت به راهکار فعلی داشته باشد.

نسخه فعلی `sentinel/discovery.py` به صورت آفلاین:

- فقط نمونه‌های آفلاینِ دارای رضایت را می‌گیرد.
- نمونه‌های دارای credential شناخته‌شده را حذف می‌کند.
- فقط موارد `unknown` را وارد clustering می‌کند.
- normalization + توکن‌های غیررایج + شباهت Jaccard روی مجموعه کلمات؛ grouping با connected components و `min_samples`.
- خروجی فقط شمارش و `top_terms` است، نه متن کامل پیام‌ها، شناسه کاربر یا پروژه.
- هر گروه `human_review_only` است؛ auto-retraining، auto-promotion، به‌روزرسانی قوانین یا اجازه ابزار رخ نمی‌دهد.

**آزمایش‌های بعدی اگر حجم واقعی داده رضایت‌داده‌شده کافی باشد:** برچسب‌گذاری دستی، ارزیابی embedding multilingual + HDBSCAN، purity/coherence، noise rate، بررسی حفظ حریم خصوصی و کنترل drift. embeddingها هم ممکن است اطلاعات حساس را بازنمایی کنند؛ قبل از ارسال متن به provider باید قرارداد محرمانگی و رضایت بررسی شود.

## ۵. سنجش کیفیت مورد نیاز

Golden testها در `tests/test_intent_experience.py` و تست جریان کامل در `tests/test_conversation.py` هستند. برای acceptance اصلی باید موارد زیر محاسبه و **با نتیجه واقعی** گزارش شوند:

- **Safety:** صفر اجرای write بر اثر پیام مبهم، متن «بله»، درخواست حذف و class hallucination.
- **Known intent precision و recall:** به تفکیک دسته‌ها، نه فقط accuracy کل؛ خطاهای incident ↔ deploy بحرانی‌ترند.
- **Unknown abstention:** وقتی متن خارج از دامنه است، پاسخ شفاف باشد و حدسی به یکی از ابزارها فرستاده نشود.
- **Multi-intent:** هیچ قصد مستقلی بی‌خبر حذف نشود.
- **Entity/mode:** نبودن project در Live منجر به انتخاب project شود؛ Demo در هیچ کارت با Live اشتباه نشود.
- **Conversation state:** انتخاب پروژه و مشاهده thread محفوظ، approval قدیمی قابل‌استفاده مجدد نیست، expiry روشن.
- **UX:** موبایل ۳۲۰ تا ۱۴۴۰ پیکسل، tab/focus، سرعت راه‌اندازی، عدم گیج‌شدن کاربران تازه‌کار، اجتناب از وعده هزینه و مانیتورینگ نادرست.
- **Clustering:** نرخ noise، پایداری گروه‌ها، خطای overmerge و هزینه بازبینی انسانی؛ هیچ cluster آنلاین auto-authorize نیست.

```bash
python -m pytest -q tests/test_intent_experience.py tests/test_conversation.py
python -m pytest -q
cd frontend && npm ci && npm run build
```

## ۶. محدودیت‌های کنترل‌شده

- Regexهای چندزبانه baseline هستند، نه درک تضمینی تمام صورت‌های گفتار. برای پیام‌های نامشخص مسیر امن وجود دارد.
- secret redaction پوشش صددرصدی تمام انواع credential نیست؛ سرور باید محرمانگی، retention و DLP را تقویت کند و کاربر تشویق شود کلید واقعی را فقط در تنظیمات امن نگه دارد.
- Clustering فقط آفلاین و برای نمونه‌های دارای رضایت است، نه روی کل تاریخچه مخفی کاربران.
- classifier جدید هنوز در محیط واقعی Liara یا مرورگر/runner سبز اثبات نشده است. **ادغام PR #26 تا رفع release gates توصیه نمی‌شود.**
- ریسک‌های مسیر VPS و احراز هویت عمومی در `docs/22-release-readiness-audit.md` باقی‌اند.

 
## ۷. اجرای Clustering فقط روی نمونه‌های مجاز

```bash
python scripts/review_intents.py --demo
# Only on a redacted, manually curated and consented JSON array:
python scripts/review_intents.py --consented-input consented-curated.json --acknowledge-consent
```

این دستور **هیچ پیام کاربر را از SQLite یا Log نمی‌خواند**؛ خروجی صرفاً شمارش و عبارت‌های نمونه برای بازبینی انسانی است. فایل‌های حاوی پیام واقعی خصوصی را در Git commit نکنید. برای نسخه عملیاتی، opt-in، retention، pseudonymization و DLP جداگانه لازم است.
