# 01 · سند نیازمندی‌های محصول (PRD)
**وضعیت:** Approved for implementation planning | **بازبینی:** 2026-10-23 | **مالک تصمیم:** صاحب محصول
## ۱. مسئله و کاربر هدف
توسعه‌دهنده‌ای که برنامه دارد اما زیرساخت را نمی‌شناسد، یا مالک سرویسی که پس از انتشار با کندی و خطا روبه‌رو شده است، باید بدون دانستن نام دستورهای زیرساختی هدف خود را بیان کند. راهکار به‌جای پنهان‌کردن اقدامات، «قابل‌فهم بودن، انجام امن و اثبات نتیجه» را فراهم می‌کند.
**کاربران:** توسعه‌دهنده مستقل، تیم کوچک، مالک محصول غیرفنی، مسئول عملیاتی کوچک. **ضدکاربر اولیه:** سازمان چندمستاجری با الزامات انطباق پیشرفته (خارج از MVP).
## ۲. معیار رسمی داوری
از صورت‌چالش ارائه‌شده: یکپارچه‌سازی و کارکرد فنی ۱۰۰، هوشمندی و رفع مشکل ۱۰۰، UX برابر ۵۰، پایداری/امنیت برابر ۵۰؛ مجموع ۳۰۰. نمونه اولیه باید دست‌کم یک سناریوی واقعی را از درخواست تا اجرا یا تشخیص نشان دهد. فایل Markdown در GitHub و دموی تقریباً ۵ دقیقه‌ای الزامی است. ویدیوی بدون دمو از داوری حذف می‌شود. این اعداد «معیار برگزارکننده» هستند، نه تخمین تیم.
## ۳. گزاره ارزش
**Liara Sentinel** یک دستیار تصمیم‌یار و مجری محدود برای لیارا است: درخواست طبیعی → شناسایی پروژه/رخداد → جمع‌آوری داده قابل‌استناد → فرضیه‌ها → پیش‌نمایش عملیات → تأیید → اجرای محدود → راستی‌آزمایی مستقل.
**تمایز محصول:** «گزارش با شناسه شاهد + تحلیل اختلاف قبل/بعدِ ریلیز + اثبات بازیابی»؛ نه صرفاً چت‌باتی با دسترسی به API.

## ۵. User stories و معیار پذیرش
**US-01 اتصال:** به‌عنوان مالک حساب، می‌خواهم پروژه‌هایم را ببینم. Given توکن معتبرِ سمت سرور، When درخواست اتصال، Then پروژه‌ها بدون env values یا token به مرورگر می‌رسند. اگر 401/403 رخ دهد، متن راهنما نمایش داده می‌شود؛ هیچ fallback ساختگی به‌جای داده زنده ارائه نمی‌شود.
**US-02 تشخیص:** Given خطای HTTP 500 پس از release جدید، When «بررسی کن»، Then سیستم لاگ، تاریخچه release، events، وضعیت و منابع را در یک بازه زمانی بررسی و بین هم‌زمانی و علت تمایز می‌گذارد.
**US-03 عملیات:** Given پیشنهاد restart، When کاربر پیش‌نمایش دارای نام پروژه، اثر، ریسک و انقضا را تأیید کرد، Then فقط همان عملیات اجرا می‌شود. اگر state/payload عوض شد، مجوز رد می‌شود.
**US-04 نتیجه:** Given درخواست restart پذیرفته شد، When verifier کار می‌کند، Then فقط پس از passing probe و شواهد عملیاتی، «verified» نشان داده شود؛ در غیر این صورت failed یا inconclusive.
**US-05 اولین دیپلوی:** Given سورس پروژه آزمایشی و پیکربندی معتبر، When کاربر پیشنهاد منابع و تغییرات را تأیید کرد، Then ایجاد/استقرار/سلامت/دامنه با status هر مرحله نمایش داده می‌شود؛ مراحل شارژ حساب/رجیسترار بیرونی handoff انسانی هستند.
**US-06 کمبود داده:** اگر metric یا endpoint در دسترس نبود، یافته «unknown» شود؛ عدم وجود خطا در داده ناقص، سلامت را اثبات نمی‌کند.
## ۶. محدوده مراحل
**P0/Vertical Slice:** اتصال read-only، تشخیص سناریوی 500، جمع‌آوری چندمنبعی، Evidence IDs، policy/approval، restart آزمایشی، verify، گزارش قابل‌اشتراکِ پاک‌سازی‌شده.
**P1:** Scout برای Node/Python، پیشنهاد منابع با عدم‌قطعیت، deploy از CLI مستند، env keys و domain handoff، diff نسخه‌ها.
**P2:** Coding Agent که فقط patch/PR ایجاد کند، پیشنهاد اصلاح پیشرفته، تحلیل هزینه با تعرفه معتبرِ زمان اجرا، پایش زمان‌بندی‌شده.
**خارج از MVP:** shell عمومی برای LLM، دسترسی مستقیم به سرور تولید، مدیریت مالی/شارژ حساب، ذخیره اسرار در browser، حذف خودکار پروژه، «خودمختاری کامل» و 24/7 monitoring.
## ۷. Non-functional requirements
- عدم افشای credential، استتار داده شخصی؛ تمام خروجی‌های مدل و لاگ داده نامطمئن‌اند.
- timeout، محدودیت تعداد فراخوانی، deadline کل run، retry bounded فقط برای GET/عملیات قابل‌اثبات idempotent.
- audit با actor/action/target/hash/policy-version و correlation ID؛ بدون مقدار راز.
- جداسازی محیط demo از live؛ badge وضعیت داده با semantics واقعی.
- دسترس‌پذیری: RTL، کیبورد، پیام خطای خوانا، متنی بدون وابستگی به رنگ.
- خطای سرویس خارجی نباید باعث «تأیید جعلی بازیابی» شود.
## ۸. معیار پایان MVP
همه تست‌های P0 در `09-testing.md` پاس شوند؛ قابلیت‌ها مطابق `11-decisions.md` برچسب maturity بگیرند؛ ویدیو یک سناریوی read/diagnose/action/verify **واقعی روی پروژه قابل حذف آزمایشی** یا با برچسب صریح mock نشان دهد. ادعای اتصال واقعی فقط با evidence timestamp و redacted proof مجاز است.
