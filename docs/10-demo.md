# 10 · برنامه دموی مسابقه و تحویل
**الزام بریف:** ویدیوی حدود ۵ دقیقه؛ بدون آن اثر وارد داوری نمی‌شود. نمایش عملکرد/تأثیر مهم‌تر از نمایش سورس است. صوت و کیفیت پرزنتیشن بر امتیاز اثر دارند.
## سناریوی محوری
سرویس disposable به نام نمونه (نه production) ابتدا سالم است. نسخه‌ای کنترل‌شده مشکل 500 یا env misconfiguration تولید می‌کند. Agent پس از اتصال واقعی، تغییر release را ردیابی و علت قابل بررسی را با شناسه شواهد بیان می‌کند. کاربر اقدام محدود را تایید می‌کند؛ سیستم آن را اجرا کرده و **بازگشت سلامت را مستقلاً اثبات می‌کند**. اگر برای رفع 500 به restart نیاز نباشد، از restart نمایشی برای «درست شدن جادویی» استفاده نکنید؛ باید اصلاح مربوط به علت واقعی و سپس آزمون انجام شود. سناریوی restart مناسبِ مشکل transientِ اثبات‌شده است.

## سناریوی دوم کوتاه برای پشتوانه
- سناریوی deploy از سورس به Liara با تشخیص خودکار stack، port و plan پیشنهادی. اگر در ۵ دقیقه جا نشد، به شکل کلیپ مکمل یا نسخه کوتاه دو صحنه در ویدیو ارائه شود.
- سناریوی failure: سرویس پاسخ 500 می‌دهد و با وجود 200 API restart، verifier «failed» نشان دهد. این سناریو قدرت صداقت سیستم را به داور ثابت می‌کند.
## چک‌لیست ضبط
- نام سرویس آزمایشی و status DEMO/LIVE روی صفحه مشخص باشد.
- از رسیدن به API واقعی فیلم بگیر، ولی Authorization/کلیدها و داده شخصی هرگز نشان داده نشود.
- زمان‌بندی پردازش طولانی با editing صادقانه یا سرعت‌دادن به بخش انتظار، بدون حذف نتیجه ناموفق.
- Narration دلیل هر action و evidence را توضیح بده؛ از buzzword یا ادعای unsupported پرهیز.
- URL GitHub و ساختار docs قابل مشاهده؛ نیازی به walkthrough سورس نیست.
- خروجی تمیز 1080p، صدای واضح، نوشته قابل‌خواندن، حرکت ماوس کنترل‌شده.
## تحویل‌های مسابقه
MVP اجراشدنی، فایل‌های Markdown در repo، README با instructions، ویدیوی نزدیک پنج دقیقه و لینک GitHub. جزئیات دقیق فرمت ارسال و deadline در متن ارائه‌شده مشخص نشده‌اند و باید از برگزارکننده تأیید شوند.
## عدم قطعیت
اگر محیط live آماده نشد، خروجی mock را با همین عنوان معرفی کن، ولی از آن به‌عنوان دیپلوی واقعی یا SRE automation موفق یاد نکن. معیارهای داوری اتصال و انجام عملیات واقعی را امتیاز می‌دهند؛ دمو جعلی به ضرر اعتبار تیم است.
