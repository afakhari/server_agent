# 07 · مشخصات UX، محتوای فارسی و تعامل انسانی
## ۱. اصول
رابط نباید نقش یک پنل زیرساخت جدید با صد فیلد را بازی کند. کاربر **هدف و سرویس** را مشخص می‌کند؛ سیستم بهترین گام قابل اجرا را پیشنهاد می‌دهد و **مرز کنترل کاربر** را نشان می‌دهد. UI زیبا امتیاز جانبی است؛ سهولت، سرعت، فهم وضعیت و اعتماد در بریف صریح‌اند.
## ۲. معماری اطلاعات
سه ورودی اصلی: «سایتم را منتشر کن»، «سایت مشکل دارد»، «عملکرد و هزینه را بررسی کن». سایدبار سبک: پروژه‌ها، رخدادهای اخیر، عملیات در انتظار تأیید، گزارش‌های قبلی. در صفحه عیب‌یابی، Summary در بالای شواهد؛ raw log به‌طور پیش‌فرض جمع‌شده و redacted.
## ۳. Journey A: First Deploy
۱) پروژه را انتخاب/لینک می‌کند؛ ۲) Scout پلتفرم، port، نیازهای env و وابستگی را نمایش می‌دهد؛ ۳) پلن پیشنهادی با دلیل و برچسب «قیمت تأییدشده در زمان...»؛ ۴) مرحله لازم برای شارژ حساب/ورود بیرونی به کاربر سپرده می‌شود؛ ۵) تغییر و هزینه برای تأیید نمایش داده می‌شود؛ ۶) پیشرفت ایجاد/انتشار/بررسی HTTP؛ ۷) راهنمای رکوردهای DNS و وضعیت SSL. **اگر تنظیم دامنه دسترسی API ندارد، راهنمای دقیق داده می‌شود، نه ادعای انجام خودکار.**
## ۴. Journey B: Incident
«سایت من از دیروز کند شده» → انتخاب سرویس → زمان رخداد → کارت جمع‌بندی؛ یک فرضیه با شاهد و محدودیت → مشاهده گزینه‌های اقدام با risk → approval → progress → proof/unknown. کاربر هر لحظه می‌تواند raw evidence masked را ببیند.
## ۵. کارت تشخیص
- عنوان: «احتمال اشکال در پیکربندی اتصال دیتابیس».
- اصل مشاهده: «در لاگ ساعت … پیام … دیده شد (EV-03)».
- استنتاج: «این خطا پس از release … رخ داده؛ به‌تنهایی علیت ثابت نیست».
- ضدشاهد: «مصرف RAM به علت unit نامشخص قابل قضاوت نیست».
- پیشنهاد: «نام کلیدهای محیطی بررسی شود؛ نیازی به ارتقای فوری منابع دیده نمی‌شود».
- وضعیت: `evidence complete / partial / missing`؛ نمایش صادقانه.
## ۶. تأیید کاربر
عنوان: «تأیید ری‌استارت سرویس آزمایشی». نام project و محیط برجسته، reason با evidence، downtime possible، cost unknown if not verified، warning irreversibility و expiry. CTA «تأیید همین ری‌استارت»، CTA دوم «لغو». هرگز از «بله، انجام بده» بدون شناسایی تغییر برای operations استفاده نشود.
## ۷. مدل پیشرفت قابل نمایش
`Awaiting approval`، `Submitted to Liara`، `Observing release`، `Checking app health`، `Verified healthy`، `Unable to verify`، `Not recovered`. اگر API پذیرفت ولی probe شکست خورد «عملیات ارسال شد؛ هنوز سلامت تأیید نشده» نمایش بده، نه «موفق».
## ۸. Empty/error states
- توکن موجود نیست: «برای مشاهده سرویس‌های واقعی اتصال امن حساب لازم است»؛ قابلیت demo با برچسب Mock.
- service list خالی: «در این حساب سرویسی پیدا نشد»؛ راهنمای create.
- 401/403: «مجوز حساب معتبر نیست یا دسترسی کافی نیست».
- 429/timeouts: «داده در این لحظه قابل دریافت نیست؛ تشخیص قطعی ممکن نیست».
- داده تناقض دارد: «دو شاهد ناسازگار داریم؛ یک آزمون دیگر لازم است».
- approval expired: «وضعیت سرویس ممکن است تغییر کرده باشد؛ بازبینی مجدد».
## ۹. دسترس‌پذیری و زبان
RTL واقعی برای متن فارسی، LTR جدا برای code/path/IDs و اعداد فنی؛ keyboard focus/aria-label، minimum contrast، وضعیت مستقل از رنگ، loading cancellable، رفتار موبایل. هر status دارای عبارت متنی و timestamp باشد. از عدد confidence درصدی بدون calibration اجتناب شود.
## ۱۰. تعریف موفقیت تست UX
۵ نفر با سطح دانش متفاوت سه وظیفه را انجام دهند: دریافت تشخیص، تشخیص عملیات مورد تأیید، فهم شکست verifier. شاخص‌ها: task completion، زمان واقعی هر مرحله، خطای برداشت «submit=success»، پرسش SUS سبک و بازخورد کیفی. نتایج بعداً ثبت شوند؛ درصد ساختگی گزارش نشود.
