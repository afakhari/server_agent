# 18 · راه‌اندازی واقعی Liara Sentinel، قدم‌به‌قدم

**این راهنما مخصوص صاحب پروژه است.** پروژه در مرحله MVP است، نه آماده Production. هیچ توکن، رمز، ایمیل خصوصی، env value یا اطلاعات پرداخت را در چت/گیت‌هاب/ویدیو ارسال نکنید. CLI رایگان است ولی مصرف منابع PaaS ممکن است هزینه داشته باشد.

## ۱. اجرای بدون حساب (اول این مرحله)
Git و Python 3.12 یا بالاتر نصب باشد. برای مسیر CLI، Node.js با نسخه سازگار CLI رسمی هم لازم است. مخزن private است و باید مجوز دسترسی GitHub داشته باشید.

```bash
git clone https://github.com/afakhari/server_agent.git
cd server_agent
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/run_local.py --mode demo --check
python scripts/run_local.py --mode demo
```

در Windows PowerShell از `.venv\Scripts\Activate.ps1` استفاده کنید؛ اگر Python با فرمان `python` شناخته نمی‌شود، `py` را امتحان کنید. اتصال CLI محافظت‌شده فعلاً برای Linux/macOS/WSL2 طراحی شده است؛ حالت demo/read در ویندوز هم کار می‌کند.

آدرس `http://127.0.0.1:8000` را باز کنید. سناریوی crash و تأیید ری‌استارت نمایشی را ببینید. این کار هنوز به لیارا وصل نیست. با Ctrl+C متوقف کنید.

## ۲. ایجاد سرویس جدا و کم‌هزینه در کنسول لیارا
از https://liara.ir/ وارد حساب **شخصی آزمایشی** شوید و یک برنامه قابل حذف با نام یکتا، مثلاً `sentinel-sandbox-01` بسازید. نام ممکن است قبلاً استفاده شده باشد؛ در این صورت نام یکتای دیگری انتخاب کنید. برای برنامه نمونه پلتفرم Python و پورت 8000 مناسب است.

**موجودی، منطقه، پلن و هزینه واقعی را فقط در پنل بررسی کنید.** وجود پلن رایگان را فرض نکنید. داده مشتری یا دیتابیس اصلی به آن وصل نکنید. اگر پرداخت/شارژ لازم است، این اقدام باید فقط توسط خود شما انجام شود.

## ۳. توکن API و اتصال فقط خواندنی
از بخش API در کنسول لیارا یک کلید آزمایشی با تاریخ انقضای کوتاه بسازید. مرجع رسمی: https://developers.liara.ir/ . توکن را فقط در ترمینال کامپیوتر خود وارد کنید، نه GitHub و نه چت.

```bash
python scripts/run_local.py --mode read --project sentinel-sandbox-01
```

نام نمونه را با شناسه دقیق پروژه خود جایگزین کنید. راه‌انداز توکن را با ورودی مخفی می‌پرسد. یک **Sentinel access key** محلی نیز در ترمینال نشان می‌دهد؛ این کلید با توکن لیارا فرق دارد و فقط در prompt مرورگر محلی وارد می‌شود.

در UI حالت Live و همان نام پروژه را انتخاب کنید و «شروع بررسی شواهد» را بزنید. اگر 401/403 رخ داد، دسترسی توکن و حساب را در کنسول بررسی کنید. اگر داده‌ای در دسترس نبود، نباید موفقیت فرض شود.

## ۴. نصب و ورود CLI رسمی (Linux/macOS/WSL2)
```bash
node --version
npm --version
npm install -g @liara/cli@9.6.0
liara --version
command -v liara
mkdir -p "$HOME/.sentinel-liara-cli"
chmod 700 "$HOME/.sentinel-liara-cli"
HOME="$HOME/.sentinel-liara-cli" liara login
HOME="$HOME/.sentinel-liara-cli" liara account list
```

اگر login مرورگری ممکن نبود، `liara login --help` و گزینه interactive را بررسی کنید. رمز و ایمیل را به‌عنوان آرگومان فرایند وارد نکنید. نام مستعار حساب (ACCOUNT_ALIAS) را از لیست بگیرید و با دستور زیر تأیید کنید:

```bash
HOME="$HOME/.sentinel-liara-cli" liara account whoami --json --account ACCOUNT_ALIAS
```

باید همان **حساب شخصی** توکن API باشد؛ CLI با حساب تیم در MVP عمداً متوقف می‌شود. خروجی JSON شامل ایمیل است: آن را اینجا یا در ویدیو منتشر نکنید.

## ۵. انتشار کنترل‌شده روی برنامه موجود
سرور قبلی را با Ctrl+C متوقف کنید. سپس بعد از جایگزین‌کردن نام واقعی پروژه و حساب:

```bash
python scripts/run_local.py \
  --mode test-cli \
  --project sentinel-sandbox-01 \
  --cli-home "$HOME/.sentinel-liara-cli" \
  --cli-account ACCOUNT_ALIAS \
  --cli-bin "$(command -v liara)"
```

توکن در ترمینال مخفی دریافت می‌شود. برای مسلح‌کردن دسترسی آزمایشی باید عبارت `ARM sentinel-sandbox-01` را دقیق تایپ کنید. **این کار هنوز خودش دیپلوی نمی‌کند**.

در رابط:
۱. در بخش «استقرار هدایت‌شده»، Backend را «CLI رسمی» انتخاب کنید.
۲. مسیر نسبی پروژه `fastapi-shop` است، زیرا workspace پیش‌فرض پوشه `examples` است.
۳. پروژه = همان شناسه موجود لیارا؛ پلتفرم = Python؛ پورت = 8000.
۴. پیش‌نمایش را باز کنید. نام حساب CLI، فایل‌ها، SHA256، ریسک و هزینه تأییدنشده را بررسی کنید.
۵. فقط بعد از بررسی، نام پروژه را دوباره تایپ و انتشار را تأیید کنید.
۶. وضعیت `SUBMITTED / NOT_VERIFIED` یعنی فقط ارسال درخواست؛ نتیجه واقعی هنوز نیازمند بررسی است.

در خطا/timeout بدون بررسی تاریخچه release **دوباره انتشار را اجرا نکنید**.

## ۶. بررسی سایت و وضعیت انتشار
در UI «بررسی نتیجه انتشار» را باز کنید. برای سنجش مستقل، در اجرای مجدد می‌توانید URL سلامت واقعیِ متعلق به همان برنامه را تعیین کنید:

```bash
python scripts/run_local.py \
  --mode read \
  --project sentinel-sandbox-01 \
  --health-url https://YOUR-OWN-DOMAIN.example/health
```

دامنه نمایشی را با نشانی HTTPS واقعی و مالکیت خودتان جایگزین کنید. اگر دامنه اختصاصی ندارید، دامنه رسمی‌ای را که کنسول برای همان پروژه نشان می‌دهد و مسیر سلامت معتبر دارد استفاده کنید. نتیجه `OBSERVED_HEALTHY_ONCE` صرفاً یک پاسخ سلامت در یک لحظه است؛ نتیجه `INCONCLUSIVE` نیز نشانه کافی‌نبودن شواهد است.

## ۷. دمو برای داوری
روی **برنامه آزمایشی** یک خرابی کنترل‌شده و برگشت‌پذیر بسازید؛ نسخه/لاگ/زمان خطا را ضبط کنید. Sentinel Live را برای تحلیل اجرا و فرضیه‌ها را با Evidence IDs نشان دهید. تغییر اصلاحی را فقط پس از تأیید انجام دهید و سلامت واقعی را دوباره بررسی کنید. برای missing env، ری‌استارت کورکورانه راه‌حل نیست؛ اصلاح باید به علت واقعی مربوط باشد. اگر اصلاح در کنسول به‌صورت دستی انجام شد، در ویدیو صادقانه اعلام کنید.

## راه‌حل خطاهای رایج
| خطا | راهکار |
|---|---|
| GitHub Permission denied | با حساب مجاز به مخزن private وارد شوید |
| Python import error | virtualenv و requirements را بررسی کنید |
| UI باز نمی‌شود | localhost/پورت 8000 و ترمینال سرور را بررسی کنید |
| Live API 401/403 | کلید API یا دسترسی حساب را دوباره بررسی کنید |
| CLI identity mismatch | توکن API و CLI باید همان حساب شخصی آزمایشی باشند |
| CLI account team rejected | برای MVP از حساب شخصی جداگانه استفاده کنید |
| Not enough balance | پلن و بودجه را خودتان در کنسول بررسی کنید |
| Release submitted but HTTP 500 | لاگ و release را بخوانید؛ بدون بررسی دوباره اجرا نکنید |
| Verify inconclusive | URL سلامت/HTTPS/DNS و endpoint برنامه را بررسی کنید |

## چه اطلاعاتی می‌توانید برای ادامه ارسال کنید؟
سیستم‌عامل و نسخه Python/Node؛ اینکه دموی محلی باز شد یا نه؛ وضعیت کلی Live read (موفق/401/403/5xx)؛ نتیجه CLI بدون خروجی whoami؛ و وضعیت نهایی SUBMITTED/OBSERVED_HEALTHY_ONCE/INCONCLUSIVE. **هیچ توکن، access key، رمز، متن کامل لاگ یا اطلاعات مالی نفرستید.**

## سناریوی خطای واقعی کنترل‌شده برای فیلم داوری
نسخه نمونه `examples/fastapi-shop/main.py` به‌صورت پیش‌فرض سالم است. برای ایجاد یک خطای **واقعی HTTP 500** و stacktrace قابل مشاهده در سرویس آزمایشی، پس از اینکه اولین انتشار سالم انجام شد:

۱. فقط در تنظیمات **همان پروژه disposable** در پنل لیارا، متغیر `SENTINEL_REQUIRE_DEMO_FLAG=true` را اضافه کنید. متغیر `SENTINEL_DEMO_FLAG` هنوز تعریف نشده یا خالی باشد. این متغیرها محرمانه نیستند.
۲. مطابق رفتار واقعی پلتفرم، انتشار/اعمال تنظیمات را در همان سرویس آزمایشی تکمیل کنید. آدرس `/health` و `/` هنگام اجرای آن تنظیم با خطای HTTP 500 مواجه می‌شوند و پیام `missing environment variable SENTINEL_DEMO_FLAG` در stacktrace سرور تولید می‌شود.
۳. Sentinel را در حالت Live بررسی کنید. فرضیه missing configuration باید با شواهد لاگ قابل ردیابی باشد؛ اگر API logs/ساختار پاسخ در حساب شما کار نکند، آن را به‌عنوان مشکل قرارداد ثبت کنید، نه تشخیص موفق.
۴. کار اصلاحیِ فعلی **دستی و صریح** است: در همان پنل آزمایشی، `SENTINEL_DEMO_FLAG=ready` قرار دهید و تغییر تنظیمات را اعمال کنید. لازم نیست مقادیر سری را جایی نمایش بدهید.
۵. مشاهده کنید که `/health` دوباره HTTP 200 می‌دهد؛ وضعیت Releases و پروب مستقل را نیز نشان دهید. اگر پلتفرم envها را با replace تنظیم می‌کند، بقیه کلیدهای پروژه را حفظ کنید.
۶. پس از فیلم‌برداری، `SENTINEL_REQUIRE_DEMO_FLAG=false` یا حذف آن را انجام دهید و صحت سلامت پروژه آزمایشی را دوباره بررسی کنید.

**نکته داوری:** این نسخه از Agent تشخیص را خودکار پیشنهاد می‌دهد، ولی اصلاح missing env در این سناریو عمداً با اقدام انسان در کنسول انجام می‌شود. آن مرحله را در فیلم «اصلاح خودکار Agent» معرفی نکنید. ری‌استارت کورکورانه برای missing env راهکار صحیح نیست. این قابلیت تنها برای سرویس آزمایشی ساخته شده است؛ هرگز روی تولید فعال نکنید.
